1. Contexte du projet

Ce projet d'auto-formation s'inscrit dans une démarche personnelle DevOps / SISR. L'objectif est de concevoir, déployer et sécuriser un serveur multimédia privé entièrement conteneurisé sur une machine virtuelle locale. La stack repose sur deux services Docker orchestrés : Jellyfin (serveur multimédia) et Nginx Proxy Manager (reverse proxy), communiquant sur un réseau Docker isolé.

PARTIE I

Infrastructure Système

Provisionnement VM, IP statique, durcissement SSH avec clé Ed25519.

PARTIE II

Environnement Docker

Installation Docker Engine via dépôt officiel, Docker Compose, gestion des droits.

PARTIE III

Déploiement IaC

Arborescence de persistance, rédaction du docker-compose.yml, mise en production.

PARTIES IV–VI

Exploitation & Synthèse

Configuration NPM, initialisation Jellyfin, injection de médias, synthèse de sécurité.

2. Infrastructure système - Socle

La VM SRV-MEDIA-01 est créée sous VirtualBox avec 2 Go de RAM et un disque VDI dynamique de 20 Go. L'adresse IP est fixée statiquement pour éviter toute perte de référence par le reverse proxy en cas de renouvellement DHCP. Le service SSH est immédiatement durci.

debian@SRV-MEDIA-01:~$ 
# Vérification de l'IP statique après configuration
ip -c a
2: enp0s3: inet 192.168.1.23/24 brd 192.168.1.255 scope global enp0s3

# Tests de connectivité (Recette T-02)
ping -c 3 192.168.1.1 && ping -c 3 google.fr
✓ 0% packet loss — Passerelle et DNS opérationnels

Le durcissement SSH (Hardening US-03) désactive l'authentification par mot de passe, interdit la connexion root, et déplace le service sur le port 2222 pour limiter l'exposition aux scans automatiques. L'accès ne se fait plus qu'avec une paire de clés Ed25519 générée depuis le PC Windows.

PowerShell (PC Windows) 
# Génération de la paire de clés Ed25519
ssh-keygen -t ed25519
→ Clé privée : C:\Users\..\.ssh\id_ed25519
→ Clé publique : C:\Users\..\.ssh\id_ed25519.pub

# Copie de la clé publique sur la VM
ssh-copy-id -i ~/.ssh/id_ed25519.pub debian@192.168.1.23
✓ Clé autorisée — connexion sans mot de passe opérationnelle

# Connexion sur le nouveau port
ssh -p 2222 debian@192.168.1.23

3. Environnement Docker & Architecture IaC

Docker Engine est installé via le dépôt officiel avec signature GPG. L'utilisateur debian est ajouté au groupe docker pour éviter tout usage de sudo. L'arborescence de persistance garantit la conservation des données entre les redémarrages des conteneurs.

debian@SRV-MEDIA-01:~/mediaserver$ 
# Arborescence de persistance (US-07)
mkdir -p config/npm config/jellyfin data/media

# Déploiement de la stack (US-09)
docker compose up -d
[+] Running 3/3
 ✔ Network media-network      Created
 ✔ Container nginx-proxy-manager  Started
 ✔ Container jellyfin             Started

# Vérification des états
docker ps
CONTAINER ID   IMAGE                       STATUS
a1b2c3d4e5f6   jc21/nginx-proxy-manager    Up (healthy)
f5e4d3c2b1a0   jellyfin/jellyfin           Up (healthy)

Le fichier docker-compose.yml définit les deux services sur un réseau isolé media-network. Jellyfin s'exécute avec l'UID/GID 1000:1000 de l'utilisateur système pour garantir les droits en lecture sur le volume de médias.

4. Architecture des services

Le Reverse Proxy est le point d'entrée unique de l'infrastructure. Les clients n'accèdent jamais directement au port technique 8096 de Jellyfin — Nginx Proxy Manager route les requêtes HTTP (port 80) vers Jellyfin via son nom de conteneur sur le réseau Docker.

Nginx Proxy Manager

Point d'entrée unique. Gère le routage HTTP/HTTPS et filtre les exploits communs. Interface d'administration sur le port 81.

:80 → HTTP publique · :81 → Admin NPM · :443 → HTTPS
Jellyfin

Serveur multimédia open-source. Accessible uniquement via NPM sur le réseau interne media-network. Port technique masqué.

:8096 → interne uniquement (non exposé hôte)
Réseau media-network (Bridge)

Les conteneurs communiquent par leur nom (jellyfin) — NPM résout l'IP interne dynamiquement. Aucun des ports de Jellyfin n'est exposé directement sur l'hôte.

5. Configuration du Reverse Proxy

Via l'interface web de NPM (http://192.168.1.23:81), un Proxy Host est créé pour router le trafic entrant vers Jellyfin. La fonctionnalité Block Common Exploits est activée pour filtrer automatiquement les requêtes malveillantes courantes.

  • Domain : 192.168.1.23 ou nom local media.lan
  • Scheme : http
  • Forward Hostname : jellyfin (nom DNS interne Docker)
  • Forward Port : 8096
  • Block Common Exploits : activé

Jellyfin est désormais accessible directement sur http://192.168.1.23 sans préciser de port.

6. Injection de médias via SFTP - Validation T-03

La validation finale consiste à transférer un fichier vidéo depuis le PC Windows vers la VM, puis à vérifier que Jellyfin l'indexe correctement. WinSCP est utilisé avec la clé privée convertie au format .ppk via PuTTYgen.

  • Outil : WinSCP avec authentification par clé Ed25519 (.ppk)
  • Connexion : Hôte 192.168.1.23 / Port 2222 / Utilisateur debian
  • Cible : /home/debian/mediaserver/data/media/
  • Volume Docker : Ce dossier est monté dans le conteneur Jellyfin sous /media

7. Synthèse de la sécurité appliquée

L'infrastructure a été conçue selon le principe du moindre privilège et de la défense en profondeur, avec plusieurs couches de sécurité indépendantes.

Accès SSH

Clé Ed25519 sur le port 2222. Authentification par mot de passe et connexion root désactivées dans sshd_config.

Isolation réseau

Services sur un réseau Docker bridge media-network — non accessible directement depuis l'extérieur.

Reverse Proxy

NPM est le seul point d'entrée. Masque les ports techniques et filtre les exploits communs.

Droits fichiers

Jellyfin s'exécute avec l'UID 1000 — pas de conteneur en root. Volumes montés avec droits restreints.

9. Perspectives d'évolution

Ce projet constitue une base DevOps évolutive. Les étapes suivantes sont envisagées pour monter en compétences :

  • Supervision (EPIC 4) : Intégration d'une stack Prometheus & Grafana pour monitorer l'utilisation des ressources en temps réel.
  • Automatisation (EPIC 5) : Utilisation d'Ansible pour automatiser le déploiement de cette configuration sur n'importe quel nouveau serveur Linux.
  • Accès distant sécurisé : Mise en place d'un tunnel WireGuard ou Cloudflare Tunnel pour accéder aux médias hors du réseau local sans ouvrir de ports sur la box.
